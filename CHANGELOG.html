Two release blockers found by the pre-publication security review

2026-09-23
  • Anyone could have made themselves the admin. An old password sign-up route, unused by the app but still open to the internet, let a stranger register using the admin's own email address. The server then treated them as the admin: every applicant's email, institution and phone, and the power to approve or reject anyone. Changing one letter to a capital defeated the "email already taken" check, so it worked even with the real admin in place, and the fake admin could not be removed from inside the app. Both legacy routes are deleted, and admin now additionally requires a Google-verified identity.
  • The video frame interval was passed to ffmpeg unchecked. It is placed directly into the command the server runs, so a crafted value could add extra instructions, for example rendering a server configuration file onto the extracted frames, which land in the requester's own project where they can be viewed. It is now validated as a number at the request and again in the worker.
  • Both were found by an independent security review of the branch and each was confirmed by a second, adversarial check before being fixed.

Authorization gaps closed, dead controls removed

2026-09-23
  • Five authorization gaps fixed. Owning one thing was letting a request reach another project's, or another account's, data: a class id attached to someone else's annotation, unchecked tags on upload, and most sharply, a video-slice request that could name any storage key, which the worker downloads and then deletes. Each was proven with a real request first, then re-tested after the fix. A denied account could also re-open its own access request forever, undoing the admin's decision; it now cannot.
  • 945 lines of dead UI removed. Undo and redo that could never record anything, a filter menu nothing read, and a 339-line export panel that could not be opened. The shortcut list now shows only the keys that work, and the sidebar button that opens it actually opens it.
  • A real performance bug found on the way: dragging one box fired an API write per mouse-move. Thirty moves, thirty requests, and only about three of them applied, because each waited on its own response. It is now one request per drag, and the whole movement is saved.

README rebuilt as the front door, and the claims behind it checked

2026-09-22
  • README: rewritten around what the system actually does. A picture-led walkthrough of the five workflow steps, capability tables, the access-control story, keyboard shortcuts, and the setup, configuration and deployment sections refreshed. All screenshots are current in-app captures; the old set predated the creation wizard and the light theme.
  • CIVAD spelled out: the Construction Industry Vision Alberta Dataset, over 50 classes and more than 86,905 images, with the ISARC 2025 citation and the co-authors credited by name.
  • Claims checked against the code: the export dialog described png_masks as producing PNG images (it produces a colour map and metadata JSON), and its "Include images" checkbox did nothing. Both now tell the truth.
  • Production bug found on the way: the api and worker containers did not share the exports folder, so every export download would have failed on a self-hosted deployment. They now share a volume.
  • Docs: the four access-control and admin routes were missing from the API reference. Added, along with the approval gate's behaviour.
  • Second accuracy pass: a fresh read of the code caught four more wrong statements, two of them in the new README: bf16 autocast is off by default on CUDA, and the macOS one-click launcher does not use Docker (it needs Homebrew Postgres 16, Redis and a MinIO binary). Also corrected: the security note now lists the deliberately public status routes, and the export wizard's PNG-masks preview no longer claims to write PNG files.

Light theme is now the default

2026-09-21
  • What changed: the app used to follow the visitor's device setting, so anyone on a dark-mode laptop saw the dark UI first. It now opens in the light theme. The Light / Dark / System toggle still works as before.
  • Existing visitors: a one-time reset moves browsers still carrying the old "system" default to light. A theme the visitor picks after that is kept, and a deliberate "dark" choice is never overwritten.
  • Bug caught while testing: the reset first ran inside React's state initializer, which React calls twice in development, so it cancelled itself out and the page stayed dark. Moved to run once at page load.

Verified three cases in a browser emulating a dark-mode device: new visitor (light), returning visitor carrying the old "system" default (light), visitor who chose dark (stays dark).

Lint works again: one shared ESLint config for the whole repo

2026-09-21
  • What was broken: bun run lint failed everywhere. The API had a lint command but no linter installed, so it downloaded a newer ESLint that refused the old settings format. The web app had an old ESLint and no settings file at all. The root command also crashed on packages/shared, which has no lint script.
  • What changed: a single eslint.config.mjs at the repo root now covers both apps. ESLint 9 plus typescript-eslint are installed once at the root instead of per app. Rules are deliberately relaxed, so the linter flags real leftovers (unused imports and variables) as warnings rather than blocking the build.
  • Result: bun run lint exits cleanly at the root and in each app. 55 advisory warnings, 0 errors. No application code was rewritten.
